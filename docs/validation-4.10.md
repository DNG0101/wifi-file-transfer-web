# Version 4.10.0 validation

Validated on 2026-09-13 before publishing.

## Checks performed

36 distinct logic checks passed in the available JavaScript execution environment:

- 17 transfer scenarios in `tests/transfer-matrix.mjs`: cancellation by either endpoint before acceptance and during an outstanding disk write; repeat multi-file sends; cancellation while opening storage, writing sender metadata, verifying a file, and before channel opening; separate control-channel cancellation when the file channel drops cancellation; concurrent A→B/A→C, A→B/C→B, A→B/B→A and independent A→B/A→B channels; decline isolation; pause/cancel isolation; corrupt multi-block retransmission; receiver pause/resume. The same 17 scenarios also passed against the shipped bundle's BlockTransfer class.
- All 11 existing `tests/block-transfer.test.mjs` cases passed: SHA-256 checkpoints and large counters, 10 GiB metadata, binary/empty files, corruption retries, verified-block reconnect, consent, pause/resume, quota failures, changed-source rejection, backpressure, and direct-save policy.
- Five application controller checks passed against functions extracted from `src/app.js`: parallel peer queues with ordered per-peer batches, independent transfer buttons, cancellation barriers and repeat sends, queued incoming approvals, identity checks and rejection of delayed cancelled channels.
- Three approved/remembered control-channel checks passed: cancellation in both directions without disconnecting approval, unknown-peer rejection and listener cleanup, remembered peer identity verification.

The transfer checks used the repository's pinned noble SHA-256 and checkpoint implementation, in-memory file/storage and connection doubles, and controlled timers. The block digest used the same SHA-256 library in place of browser WebCrypto. This tests protocol and cleanup logic, not actual browser storage or WebRTC performance. The normal Node test entry points import the real source dependencies.

Syntax checks passed for changed JavaScript and the shipped bundle. The readable source implementations for BlockTransfer, TrustedDevices, MainPeerManager and the application are synchronized into the existing dependency bundle. HTML and service-worker references both use version 4.10.0; the shell cache is v22. The old global highest-history percentage script was removed; the application now displays aggregate progress for active transfers.

## Execution limits

The local process runner failed before execution with `helper_unknown_error: apply deny-read ACLs`. Consequently `npm test`, esbuild, Playwright, physical-device transfers, actual browser downloads/OPFS/IndexedDB, TURN/international network paths, mobile browsers, throughput benchmarks and physical very-large-file transfers were not run in this session. The browser bundle was synchronized and exercised as described above, not regenerated by a successful esbuild invocation.

A finite simulated matrix does not establish every browser/network/peer-count combination. No speed multiplier or 1 TiB browser-capacity claim is made.

## Reproduce on a working development machine

Run `npm ci`, `npm test`, `npm run build`, and the repository's relevant browser suites. Exercise at least three distinct browser profiles/devices: A sends to B and C together; B sends back to A during that transfer; cancel either endpoint mid-file, immediately choose new files for that peer, and verify that C continues. Repeat during pause, slow storage, offline/reconnect, folder sharing and multiple-download prompts. Verify final hashes and device Downloads, then refresh and confirm completed temporary copies disappear.
